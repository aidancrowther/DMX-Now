# Feature 8 — ENTTEC Serial Input Hardware Test Plan

## Goal

Verify the existing `transmitter/transmitter.ino` Feature 8 parser end-to-end:

```text
Host Python (57600 8N2 ENTTEC framing)
  -> ESP8266 transmitter UART0
  -> ESP-NOW transmitter/receiver link
  -> receiver MAX3485 DMX output
  -> Arduino Mega USART1 / DMXSerial monitor
  -> host Python (115200 USB control/results)
```

The test monitor is deliberately separate from the DMX source. It verifies the
actual wired DMX generated by the receiver after wireless reconstruction.

## Wiring

| Connection | Required wiring |
|---|---|
| PC to TX | `/dev/ttyUSB0`, 57600 baud, 8N2. |
| Receiver DMX to Mega | receiver MAX3485 **RO/data** to Mega pin 19 (`RX1`); shared signal ground. |
| PC to Mega | `/dev/ttyUSB1`, USB serial, 115200 baud. |

Builds pass `-DDMX_USE_PORT1` globally, so `DMXSerial` binds USART1 and leaves
USB `Serial` for the test command/result channel.

## Run

```bash
python3 -m pip install --user pyserial  # if `import serial` fails
python3 Testing/feature8/tools/run_hardware.py --deploy
```

`--deploy` flashes only the **transmitter** and Mega monitor. It does not flash
or modify the receiver. A timestamped `manifest.json`, individual result JSON,
and deployment logs are written under `Testing/feature8/runs/`.

## Automated acceptance tests

| ID | Source stream | Expected Mega verification |
|---|---|---|
| F8-01 | 512-slot ramp, delivered in uneven serial chunks | every captured DMX frame matches all 512 channels. |
| F8-02 | 37-slot ramp | slots 1–37 match; slots 38–512 are zero. |
| F8-03 | nonzero start code, wrong terminator, oversized declared length | last valid 37-slot universe remains output. |
| F8-04 | valid 512-slot constant frame after F8-03 | parser has re-synchronized and output matches all 512 channels. |

The Mega emits one `RESULT` per recording window. A passing result needs
`checks > 0` and `fail = 0`; `no_data` detects a dead DMX link.

## Compile-only verification

```bash
./flash_transmitter.sh
./flash_enttec_dmx_monitor.sh

```

## Receiver build mode (required for Feature 8)

`receiver/receiver.ino` defaults to **production validation**. It accepts an
arbitrary DMX universe only after the existing structural checks succeed: valid
wire protocol/header, canonical non-overlapping fragments, every expected
fragment, and full 512-byte coverage. This is the required mode for Feature 8:

```bash
./flash_receiver.sh -f --port /dev/ttyUSB<receiver-port>
```

No `--define` is required for Feature 8 or normal DMX use.

For isolated legacy Feature 5 deterministic-pattern tests only, compile the
optional content gate explicitly:

```bash
./flash_receiver.sh --define -DRX_VALIDATE_TEST_PATTERN=1
```

That opt-in build additionally requires
`stagingUniverse[i] == (i + frameSequence) & 0xFF`, and will reject ordinary
ENTTEC lighting values. Do not flash that test configuration for Feature 8.

### Prior hardware observation (2026-09-03)

Before production validation was made the default, the prior receiver build
still had the deterministic gate always enabled. The Mega saw live DMX (`133`
complete frames per three-second window), but arbitrary ENTTEC expectations did
not promote. That run is not Feature 8 acceptance evidence; re-run the suite
with the current default receiver build and retain its new manifest.
